An independent, approachable Windows desktop-use game player and overlay. The
user selects a running game as a workspace, records and reviews demonstrations,
builds and tests reusable game packs, and can eventually run bounded specialists.

playback of a fixed action sequence is not autonomous play. AI helps bootstrap
perception and research but is not assumed reliable or fast enough for every task.

## Working rules

- Complete a vertical slice and its evidence before broadening scope. Do not call
  scaffolding a feature, or a build/test success a live gameplay success.
- Reuse existing Emgu/OpenCV, Tesseract, legacy code and reviewed upstream projects
  where verified; preserve provenance and check binary/model licenses.
- Keep the capture, encoder, perception, decision, action and review interfaces
  replaceable. Game packs contain bounded data, not arbitrary downloaded commands.
- Preserve user data and existing sessions; do not overwrite labeled originals.
- No dependency on cloud, accounts, Firecrawl, a specific game, or a particular
  model for the core app. Optional providers must disclose setup and data flow.
- Each milestone requires a usable entry point, failure handling, appropriate
  automated tests, documentation and a packaged-build check where relevant.

## Gate 1 — real-time recording foundation (current critical path)

2026-10-30 probe: `--verify-video-probe` captures an animated owned test window
off the UI thread through the existing Windows Graphics Capture path, sends frames
through a bounded buffer to a locally installed FFmpeg, and writes video and
capture/encoded timestamp arrays. A first fixed-60-fps encoding incorrectly made
five seconds play in 1.92 seconds. A second prototype used encoder-arrival
timestamps: 168 frames over 4.72 seconds, 0 buffer rejections, 4.70 seconds of
playback. This is a controlled test, not a 60 fps guarantee; arrival timestamps
are not the original capture timestamps. It is not integrated into the workspace,
does not record inputs, and does not bundle FFmpeg. Failure, sustained load,
privacy, packaged build and Wizard101 qualification remain open.

Further controlled probes: batched frame writes produced 157 captured, 155
submitted and 2 buffer rejections, but the output held only 152 frames. A subsequent
passthrough/time-base experiment wrote 168 of 168 submitted frames, 0 queue
rejections, with 4.56 seconds of capture spanning a 4.50-second video (~36.6 fps).
The sidecar now distinguishes submitted frames from independently verified video
frames and reports gap percentiles. These experiments still use encoder-arrival
timestamps for video PTS, not authoritative compositor timestamps; they are not a
finished recording implementation, and neither result establishes 60 fps.

The probe now independently inspects the finished video with the `ffprobe.exe`
next to the selected FFmpeg executable. Its sidecar reports decoded frame count
and duration; an unreadable video or a mismatch with submitted frames fails the
probe, and capture initialization failures also leave a failed timing report.
A final controlled 640×360 test captured and submitted 172 frames, independently
verified 172 video frames over 4.584 seconds, and reported no queue rejections.
Measured capture was about 36.8 fps over 4.642 seconds (p95 gap 44.4 ms). A
restricted capture attempt also produced a failed sidecar and nonzero exit status.
These are development-probe results, not an installed workspace feature or a
Wizard101 test; video timing still follows encoder arrival rather than capture.

Subsequent work adds an experimental Observe video preview backed by Windows
Media Transcoder. Each sample carries its compositor timestamp; ffprobe checks
decoded frame count and playback timestamps. A controlled 1280×720 animated
window produced 243 verified frames across 4.742 seconds (51.0 fps overall), no
queue rejections, p95 capture gap 22.2 ms and p95 playback timing error 0.015 ms;
the maximum capture gap was 517 ms. This short test does not establish sustained
60 fps, and misses in the OS capture pool are not counted as queue rejections.
The capture path now reuses a bounded pool of pixel buffers to reduce repeated
large managed allocations. Two subsequent 1280×720 runs measured 47.1 and
43.9 fps overall with no queue rejections; these brief, variable runs do not
demonstrate a throughput improvement or 60 fps.
The experimental video button has a three-minute limit and records no audio or
inputs. A separate local-video import extracts up to 600 frames at 1–10 frames
per second (default 5) from up to three minutes into the existing label/pack
workflow, with approximate video times; sampling can miss short events. A controlled end-to-end check exercised
Observe start/stop, video verification, sample import, a human label and pack
export. The same controlled workflow passed from a portable package with private
FFmpeg. An isolated installer lifecycle check preserved recording and video
sentinels as well as packs and reports through update and uninstall. These checks
did not use Wizard101, exercise the video file picker or qualify a clean machine.

Local vision remains offline serial pre-screening. On four previously human-labeled
Diego frames, qwen2.5vl:3b took 7.55 seconds cold then 0.73–0.78 seconds per frame;
its screen-label prompt returned only `dueling-diego` on all four, not the more
specific human labels. On two held-out frames manually sampled from Widzelli's
[How Hard is Dueling Diego?](https://www.youtube.com/watch?v=kGdfZQNkIjI) video,
the same prompt incorrectly returned `graphics-options` twice. A less leading
exploratory prompt described visible subjects more usefully on those two images
but misidentified Diego and did not reliably reproduce the four human labels;
it has not been promoted as a validated improvement. These are tiny qualitative
checks, not a general accuracy estimate or a continuous-video evaluation. At the
observed warm rate, processing every 60-fps frame would accumulate a large queue;
pre-screening is not in the capture or live decision path.

### Capture and action-suggestion experiments, October 31

A 20-second 1280×720 controlled source painted at roughly 64 updates/second;
the earlier CPU-copy path delivered approximately 36.6 fps in that run. GPU
surfaces and frame-ready callbacks improved throughput, but early tests exposed
startup rejections and an in-process warm-up resource stall. Warm-up now runs
in a supervised helper that exits before recording. The development Observe
recorder uses that GPU path; stop, stop during warm-up, target loss and resize
passed controlled tests. One separate-process 1280×720 source that painted at
about 180 Hz produced 3,703 verified frames over 60 seconds (61.7 fps), with no
queue rejections and 0.016 ms p95 playback-timestamp error. A second 60-second
separate-process run, with a brief concurrent local-vision workload, produced
3,712 verified frames (61.9 fps) and no queue rejections. A packaged preview
also produced 3,724 verified frames (62.1 fps) over 60 seconds with no queue
rejections. The timing error compares saved video timestamps with capture
timestamps; it is not a measure of end-to-end reaction latency. Queue counts do not
include frames Windows never delivers. Source paints are not equivalent to
distinct frames actually presented by the compositor. These controlled runs
do not establish general reliability, and no live Wizard101 capture was
available during this work.

A further 60-second test ran 60-fps video sampling in a separate process while
recording the animated target. Capture delivered 3,533 verified frames (58.9 fps),
with zero recorder queue rejections and a 22.2 ms p95 frame gap, while the target
painted about 178 times per second. The capture goal therefore remains unmet under
this workload; zero queue rejections do not prove all source frames were delivered.
The workspace prevents video recording and sampling concurrently in the same
window, but other processes can still compete for resources.

Subsequent 30-second Dodge menu captures averaged 57.7 fps with just the
recorder and 49.5 fps with the workspace preview active. An optional preview-paused
mode produced 43.1 fps in another run and reconnected successfully. These are
individual non-controlled runs, not proof that the option improves throughput.

A separately instrumented copy of the game reported approximately 180 render-loop
updates per second while Windows delivered only one capture frame for its unchanged
image. Thus frame-delivery rate on a static screen is not a valid measure of the
game's rendering or a reliable estimate of dropped frames. That one-frame video
was only about 17 ms long despite a much longer observation interval. In the
active desktop session the recorder now holds the last observed image through the
stop time with an explicitly marked synthetic terminal frame. A test with one
observed frame yielded a two-frame, 8.065-second video for an 8.049-second
observed interval, with no missing tail. Starting on a still screen, retaining
Observe on a static target, normal stop, warm-up cancellation, target loss and
resize passed controlled integration checks. Small clock-boundary discrepancies
are recorded rather than treated as missing footage. Observe marks old recognition
as stale, and a recording with no first frame reports a bounded failure.

With the final handoff and held-frame changes, a one-minute 1280×720 animated
test delivered 3,544 frames (59.0 fps), zero recorder-queue rejections, and no
unrepresented tail; its source rendered about 159 updates per second during the
broader test. A ten-second Observe-to-review check on the visible Dodge window
captured 598 frames (59.5 fps) with no missing tail and produced 50 review samples.
Neither result establishes reliable 60 fps, and zero queue rejections do not count
frames Windows did not deliver. Still-window startup and the preserved-ending
integration test passed twice; no gameplay action or reaction-time qualification
is implied.

On November 3, a user-played Dodge capture produced 2,692 observed frames over
about one minute (44.8 delivered fps; 51.4 fps over the visually inspected
20–30-second movement section), zero recorder-queue rejections, and a synthetic
terminal frame preserving the ending. The largest capture timestamp gap was
661 ms; a gap alone cannot distinguish unchanged content from undelivered frames.
The recording contains no synchronized keyboard events. Its 301 review samples
remain unlabeled, with eight assistant-reviewed state suggestions saved separately
for user acceptance. A short visual check of motion tracking found seven successive
direction suggestions consistent with the sampled player movement, followed by an
abstention; this small selected example does not establish general tagging accuracy.

The offline tracker now checks a borderline match in both directions before
continuing and can describe diagonal screen displacement. On the same selected
Dodge sequence it compared 55 consecutive pairs before stopping, versus eight
before the change. A separate white-eye position heuristic agreed on 51 evaluable
pairs, but is not human-labeled ground truth. Three checked stationary pairs
produced no motion label and two checks without the player were rejected. These
small, related examples do not establish action recognition or live-control safety.
The user also reported a competing RealityScan job during earlier captures, so
those throughput results should not be treated as clean-load benchmarks.

After the user reported the scan finished, a separate one-minute synthetic-window
run delivered 1,830 frames at 30.5 fps while its source averaged about 30.1 paint
updates per second. The capture callback's measured p95 execution time was 0.013 ms,
with no recorder-queue rejections. These figures suggest the callback was not the
limiting stage in that run; they do not identify why the source updated slowly or
prove that Maelstrom can sustain 60 fps on other windows. Frame-delivery and
callback timing distributions are now saved in the video timing report. Their
clocks can differ slightly, so a negative delivery delay is not a negative latency.

In a second user-played Dodge recording, 3,145 observed frames were delivered
over about 60 seconds (52.4 fps), with a 22.2 ms p95 gap and 44.4 ms maximum gap.
No recorder-queue rejections or missing ending were reported. The local vision
model was resident in GPU memory, although no inference was running during the
capture, so this is not an isolated benchmark. Windows may omit frames before
the recorder receives them. The 300 review samples are not action labels and
do not establish a playable or trained specialist.

Local AI pre-screening reuses a result only for exact duplicate images with the
same crop, while rechecking the saved image hash. The 301 sampled frames in the
user's Dodge recording have 260 distinct images and no selected crops, so this
would avoid 41 model requests if every frame is prescreened. Suggestions remain
review-only; independent check recordings cannot use them.

On five selected Dodge images, the existing local vision prompt produced a useful
game-over label, game-title labels for two menus, and incorrect settings labels for
two gameplay frames. A candidate prompt improved some gameplay descriptions but
also mislabeled other frames, and has not been promoted as generally reliable.
Another small cross-game prompt check returned repeated digits instead of useful
text. The development code now rejects degenerate screen-label responses and skips
them during batch pre-screening while continuing with later frames. Neither the
small sample nor the heuristic establishes model accuracy across games.

When the desktop was inactive, both the development version and the previously
working preview received no frames from an animated control window; both worked
again after the desktop was active. These checks do not qualify capture across all
Windows sessions, real games, or 60-fps workloads. Reflex's live test remains
unverified because Computer Use access to the local Edge window was not approved.

Review can now start at a chosen video position and sample at up to 60 frames
per second, bounded to 600 frames per import (ten seconds at 60 fps). A test
import yielded 600 frames at positions 20.000–29.983 seconds; another seek matched
the same four frames and times from the supplied video's previously sampled clip.
Sampling remains separate from recognition, and this does not establish action
tagging accuracy.

An independent animated test target remained capturable for five seconds while
fully covered (311 frames, no queue rejections). A separate same-process static
window occlusion check failed twice with no fresh frame and passed on a later
attempt. Occlusion is therefore not guaranteed: a target that stops repainting
or otherwise stops producing capture frames can still cause Observe to pause.

The local multimodal model got four selected positive frame-pair labels right
but suggested an approaching enemy for all six unchanged or reversed checks.
It is not safe to treat that result as an automatic action label. An independent
screen-relative template-motion suggestion instead uses a user-selected region,
rejects weak/ambiguous matches, stops tracking on uncertainty, and requires user
review. Initial pairs from the supplied video produced sensible left/right/up/down
motion and abstentions; in a separate short section, two visible motions were
missed and a reversed example matched correctly. These few hand-selected examples
do not establish accuracy or identify semantic actions such as jumps or attacks.
Human-taught transition suggestions compare consecutive frames using the same
fixed visual thresholds plus a signed-change similarity check; they are
review-only and returned no suggestions on the small video test clip.
Independent check recordings cannot use either suggestion path. More varied,
held-out human-labeled sequences and a real 60 fps target are still required.

Replace the UI-timer bottleneck with continuous selected-window capture off the UI
thread. Attach the compositor timestamp and target generation to each frame; use
bounded handoffs, explicit ownership and drop accounting. Add the approved private
FFmpeg backend with checked version, provenance, license and software/hardware
fallback. Record playable video and a versioned sidecar that reports frame times,
expected versus delivered frames, drops, resolution, encoder, start/stop reason,
errors and finalization state. Do not synthesize an honest-looking 60 fps file from
missing frames without recording that fact. Keep recording, preview and recognition
independent; expose failure and limits to the user.

Acceptance: a controlled moving test window and a short Wizard101 Observe session
produce playable video, intact sidecar, measured throughput and timing; reported
drops match induced overload; stop, close, resize, target loss, process failure and
disk-full handling preserve recoverable data. Benchmark 1280×720 at a 60 fps target
on this computer; report actual p50/p95/p99 timing and capture/encode drops. Do not
promise 60 fps unless measured. Packaging includes required notices and passes a
clean install/update test. Existing PNG sessions still open.

## Gate 2 — action/outcome demonstrations and review

Offer explicit opt-in input recording only for the chosen game/session. Record
timestamped key/mouse transitions, target/focus changes, coordinate space and
relevant outcomes; avoid recording unrelated windows and sensitive text. Support
video timeline playback, frame stepping, labels, regions, masks and suggestions.
Add accessible stop and storage management. Recorded actions are data, never run
automatically. Define a versioned session contract and migration from PNG sessions.

Acceptance: a controlled test reproduces a known sequence of frames, inputs and
outcomes with measured alignment; focus loss and cancellation are handled; reload
and export retain integrity. On a separate Wizard101 demonstration, the user can
see what they did and when without relying on inferred inputs.

## Gate 3 — first complete no-input workflow

From the installed app: select game, record a teaching session, review/label,
create a versioned pack, reopen it and evaluate against a separate session. Unify
Workspace and Workshop navigation; make results and failures visible. Bundle
sample data; allow users to test independently of a live game.

Acceptance: repeat the whole journey on a clean installation, plus a Wizard101
session. The second session is collected separately; report correct, incorrect,
unknown and excluded overlaps with versioned evidence and thresholds chosen before
evaluation. Packs and recordings survive update/uninstall and export/import. This
gate does not claim live action or general game intelligence.

## Gate 4 — robust perception and assisted play

Compare fixed-region and template/object/OCR approaches using the same held-out
recordings, including negatives, animated backgrounds, scale, geometry and target
loss. Support optional local vision-model suggestions with provenance and user
review. Measure latency, false positives and unknowns; detect stale model results.
Deliver a usable overlay and an Assist mode that proposes but does not dispatch.

Acceptance: tested detector quality and tail latency meet thresholds set for the
chosen game; user can inspect decisions, hide/stop the overlay and correct labels.
AI suggestions cannot silently contaminate independent test labels.

## Gate 5 — one bounded specialist, then genericity

Build one small game's specialist as a pack, including decision rules, fallback,
action ownership, target checks, deadlines, release-on-stop and outcome validation.
Use a controlled test application first; then a supervised game trial. Keep a
separate asynchronous review model; stale advice cannot trigger current actions.

Acceptance: documented successful runs, failure/recovery and user takeover on
independent trials, with task success, interventions, false actions and latency.
Only then add another game/interaction type principally through a new pack. Diego
is an important real-time target; use it when measured capture/perception/action
latency supports its deadlines, rather than assuming it is the easiest first pack.

## Gate 6 — game-learning platform

Add optional sourced research and user-editable knowledge, learned models and
specialist routing only after demonstrations/outcomes and evaluation exist. Build
repeatable offline/online experiments, dataset/version management, provenance,
model hardware checks, privacy controls and fallback. Add game library, richer
overlay, accessibility and diagnostics in support of these flows. Guidance must
distinguish cited claims from observed/verified facts.

Acceptance: an unfamiliar supported game can be added and improved through the
documented pack/workspace workflow, and a second independent game demonstrates the
shared system. No promise that arbitrary games will work immediately.
