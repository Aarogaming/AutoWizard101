# Dodge desktop input verification

On November 4, 2026, a bounded test of the owned local Dodge demo isolated an input-encoding problem. The game binds movement to physical keys. A previously accepted virtual-key left-arrow dispatch reached Godot with the logical left-arrow key code but a different physical key code; no movement was visually observed. The Windows receipt by itself was not evidence of gameplay response.

The Windows Dodge input sink now supplies a mapped physical scan code with the extended-key flag for arrows, and the same scan code on release. In a repeat test, the instrumented game received the correct physical left-arrow code. For the first pulse, game state showed the player move from x=240 to approximately x=187, while Maelstrom's separate before/after screenshots also indicated leftward movement. A second pulse moved the game's player again, but the visual tracker did not find the player afterward; the loop stopped with an unknown outcome. This establishes a limited response to the tested action, not reliable continuous play or success at Dodge.

The test used an isolated, instrumented copy of the local Godot demo, the draft Dodge pack, a focused foreground window, Windows Graphics Capture, and bounded key pulses. The test process reported approximately 0.80 seconds of game CPU time and 166 MiB peak game memory; those are not system-wide totals. The computer-use helper had to activate the test window because an unattended launch did not consistently acquire foreground focus. Windows can deny focus requests, and Maelstrom still stops rather than sending a gameplay action to an unverified target; unattended focus remains an open issue.

The run report and screenshots are in `.local/dodge-skill-eval-scancode-20261104/dodge-runs/` on the test machine. The original broader diagnostic temporarily recorded unrelated keys while its window was foreground; that raw event file was removed, and the repeat diagnostic was restricted to arrow-key events. Future diagnostics must collect only explicitly selected controls.

The owned verification now allows one action in a three-second run, stops immediately when the initial focus request fails, and never sends a new action after the run budget expires. A subsequent noninteractive check exited when Windows refused focus; it sent no inputs. This does not establish reliable unattended foreground activation. Interactive focus changes can complete asynchronously, so the workspace waits briefly after an accepted request and rechecks the target before starting; it stops when focus changes and never repeatedly takes focus back.

A later installed-build test used one computer-use activation of the owned game window and no key-event logger. The installed loop dispatched one left pulse, and its before/after screenshots showed the player move left. The process stopped at the one-action limit; its game process reported about 0.92 seconds of CPU time and 165 MiB peak memory. This is a single observed response, not a continuous-play qualification or proof that the application can activate a window unattended.

For workspace-initiated tests, Maelstrom requests activation only when it is already the foreground application; if the target is already foreground it can proceed. If another application is foreground or Windows refuses the request, the test sends no input. The foreground checks reduce accidental focus stealing but cannot make the check and Windows focus transition atomic.
