# Pet Dance continuous passive integration review

Reviewed 2026-11-09. This is a source/evidence review and implementation proposal only. No source was changed, no build or capture was run, and no desktop, audio, game settings or volume was accessed by this review.

**Later update, 2026-11-09:** the native sound-led player completed one independently checked five-round game with 25 arrow dispatches. See [the live player study](PET_DANCE_LIVE_PLAYER_20261109.md) for the measured success, preserved earlier failures, unresolved cleanup receipt and UI-size limits. The proposal below is retained as historical source review, not the current implementation status.

**Recommendation:** create a separate finite, passive observer that shares one selected-window capture among visual recognition and evidence collection, plus one selected-process audio capture. Keep visual and audio observations separate, joined by source timestamps. It must produce proposed sequences and disagreements without owning or dispatching game inputs. First qualify live raw-frame geometry; the existing recorded-video success does not establish that mapping.

## Smallest staged implementation

Suggested new API, **not yet implemented by this review**:

```csharp
Task<PetDanceObserveResult> ObserveAsync(
    GameWindow target, string profilePath, string newDirectory,
    PetDanceObserveOptions options, CancellationToken stop);
```

Options should explicitly include audio opt-in, target identity, expected capture geometry, cumulative loading/active budgets, frame-analysis ceiling and evidence limits. Do not add input permission, auto-start navigation, snack feeding or automatic settings changes to this observer. A dedicated CLI such as `--observe-pet-dance` should say observation-only in its ready and finished receipts and should construct no key sink, input pulse, input-owner scheduler ticket or desktop-activity hook. Observing human/UI actions, if wanted, is a separate opt-in.

1. **Bind and validate.** Freeze HWND + PID + process start ticks through `GameWindows.Read`/`SameIdentity`; verify W101, visibility, nonminimized state and actual WGC geometry. Save profile/reference hashes, context and source dimensions. A reused PID/handle, changed dimensions or stopped target closes this run; do not silently reattach.
2. **Observe one source.** Start one `WindowObserver`. Aim for at most 30 analyzed frames/s, using latest-frame reads and one outstanding copy. Feed each owned raw frame to `vision.Extract`, `vision.Read` and `sequence.Observe`, plus a bounded evidence selection. A cadence target is not a throughput claim: record source gaps, stale/dropped observations and processing times.
3. **Record audio once.** Start `GameAudioRecording` only when requested and bound to the same process instance. Preserve QPC, raw device positions, flags and gaps. The observed zero device position remains explicitly unqualified; do not manufacture a cursor. Stop audio with the passive run even if no gameplay was recognized.
4. **Join without claiming a video.** A raw-panel observer can call the writer's `StopAsync(videoVerified:false)` and retain a separate manifest containing `visual_source=raw-wgc`, first raw capture QPC, per-observation QPC and audio receipt path. Do not claim a verified MP4 or populate a fake video hash. Existing finalized-video analysis will need a deliberate raw-observation import path to consume this evidence.
5. **Add streaming audio features only after parity.** Add an optional nonblocking packet fork in the native recording path, using an independent bounded queue, not a second reader competing for packets on the existing WAV queue. A two-second stereo PCM ring at 44.1 kHz needs about 353 kB. Compute bounded candidate windows off the native callback. Queue overflow becomes an explicit feature gap; it must not invent continuity. Keep the disk writer and analyzer failure/cleanup statuses separate.
6. **Proposals and disagreements only.** Initially analyze audio around a visually observed Watch onset after the needed 220 ms future audio exists. Report `audio_agrees`, `audio_disagrees`, `audio_unknown` and timing uncertainty beside the visual cue. This is delayed corroboration. Continuous audio-only onset detection, negative-context tests and repeated-note boundaries are a separate qualification stage. An unknown visual round stays unqualified; audio does not silently repair it.

If an MP4 is also required, extend the existing [GpuSurfaceVideoProbe](../ProjectMaelstrom/ProjectMaelstrom/Utilities/GpuSurfaceVideoProbe.cs) pipeline with a bounded frame-analysis fork from the **same retained surface** used by its encoder. Do not run a second WGC observer beside the recorder. The callback must enqueue/retain quickly; CPU copy and recognition happen outside its capture lock. Encoder and analysis consumers each release their own `SharedLease`; overflow disposes the rejected analysis lease immediately. The recorder's `SetSurfaceReceiver` already transfers frame ownership, so a casual asynchronous callback without retained ownership is unsafe.

## Budgets, stop behavior and output contract

Default experimental budgets can remain **45 s cumulative startup/loading + 75 s active**, with an outer 120 s observation deadline plus separately reported cleanup. The capture backend's 210 s absolute audio ceiling is only a backstop for the general 180 s video workflow and its setup allowance; it should not keep this shorter observer alive. Before gameplay starts, all elapsed waiting consumes the startup/loading budget. After gameplay begins, Unknown consumes active time unless Loading is positively recognized. No-frame iterations consume wall time too. A fresh ready frame arriving at an exhausted budget does not forgive that elapsed interval.

Suggested output bounds: at most 4,000 analyzed observations, 64 scene-change panels, 16 full raw diagnostic frames, 16 additional unknown/error panels, a one-per-second progress receipt, and the existing audio queue/22,000-packet/64 MiB caps. These are proposed defaults, not claims that current trial lists are bounded this way. Record dropped evidence counts; do not grow a list indefinitely on a loading screen. Store source QPC, callback QPC, analysis start/end, source size, phase/cue/opacity/error, sequence state and undispatched proposal IDs. Write the final reason and `inputs_sent=0` independently of success in recognizing the game.

Passive observation does not require foreground ownership and should not activate W101 or reject ordinary desktop typing as an input takeover. It still stops on target replacement/minimization, requested stop, geometry mismatch, exhausted budgets or capture failure. Root's ordinary UI interactions remain separately supervised through the supported desktop tool; native Idle restoration is a separate observed cleanup outcome, never implied by the observer stopping.

**Current blocking implementation concern:** `WindowObserver.ReadPixelsAsync` holds its gate during an uncancellable GPU copy, and `DisposeAsync` waits on that gate. Checking elapsed time before the call does not guarantee prompt stop. Implement the ownership design in [capture cancellation review](WINDOW_CAPTURE_CANCELLATION_REVIEW.md) before advertising a hard stop deadline: caller cancellation detaches its wait, one owned continuation drains/disposes the eventual result, and observer disposal runs only after that operation relinquishes ownership. Record `cleanup_pending` if the owned native operation has not completed. Do not launch replacement readers or force-dispose their surfaces. Process isolation is the stronger later boundary if native calls can stall indefinitely.

## Geometry: what the measurements establish

The recorded W101 setting is 1280 × 720 with Tiny UI. The observed **whole-window WGC source is 1282 × 759**, whereas the encoded H.264 video is **1282 × 760**. `WindowObserver.GetCaptureSize` and instance `Width/Height` expose WGC dimensions; `GameWindows.ClientSize` exposes the separate client rectangle size. Current `GameWindows` does not expose client-to-capture origin or DPI. Neither a 720-pixel game setting nor the dimension ratio establishes the exact client-content offset inside the captured chrome.

The frozen profile uses full-window decoded coordinates, stacks Top `(512,100,256,40)` with Bottom `(512,646,256,100)`, and analyzes absolute phase `(525,657,232,28)`, cue `(610,680,64,64)` and feedback `(550,100,180,40)`. Its canonical dimensions are 1282 × 760. `VideoGeometry.EncodedSize` merely rounds dimensions to even values for H.264. Recent recording receipts correctly mark `source_to_video.transform_verified=false`.

The [real GDI+ diagnostic](PET_DANCE_CALIBRATION_DIAGNOSTIC.md) established that bottom-row removal followed by implicit 759→760 scaling destroyed recognition on eight study images, whereas other one-row relationships behaved differently. It did **not** determine which relationship the actual encoder applies. A one-pixel ROI shift also broke the tested frozen pixel thresholds. Therefore the current evidence cannot safely choose `preserve-pixels` or `scale-one-pixel-height`, and increasing tolerance or trying both per frame would hide the unresolved geometry.

There are two defensible next steps:

- **Prefer a new raw profile for the passive observer.** Save a small set of timestamped raw WGC panels spanning neutral, all arrows, Watch, Go and feedback using the supported supervised UI demonstration. Review and label those exact raw pixels, freeze their own 1282 × 759 profile and references, then test on a later visit. Preserve the old encoded profile and its evaluation history. This avoids depending on the encoder transform. It still needs exact UI/context qualification.
- **Measure the raw-to-encoded transform if old references must be reused.** Retain a small set of raw images from the same WGC surfaces submitted to the encoder, recording source QPC and submission index. Match decoded samples to those source images using the actual submission/encoded timeline plus visual evidence; rate-converted frame index alone is insufficient. Measure interior anchors/edges in multiple stable panels and fit one declared mapping. Test it on separate source/decoded pairs. If the measured transform is not supported by the current two-option profile schema, extend the schema explicitly rather than force-fitting it.

The raw and decoded images must depict the same sampled content; the existing Watch screenshot versus loading screenshot does not qualify a mapping. Even exact timestamp correspondence needs attention to the recorder's duplicate/terminal frames and encoded color conversion. A stable reviewed profile, not online transform selection, should define the live pixel contract.

## Acceptance evidence for the first passive run

Before live observation, test the new coordinator with fake frame/audio sources: target replacement, missing and stale frames, cumulative interrupted loading, geometry mismatch, audio gaps/queue overflow, cancellation during a pending frame copy, no callback after completion, and zero input dispatch. Compare any native streaming descriptor against the existing offline descriptor on frozen PCM windows, including silence, repeated notes, music, out-of-band energy and timestamp discontinuities.

The first supported-UI visit should produce fresh raw phase/cue observations, synchronized selected-process audio, bounded saved examples, an honest proposal/disagreement report and confirmed capture cleanup, followed by separately observed native Idle. It need not win a game to qualify passive collection. Audio and video isolation, geometry, cue accuracy, action timing and gameplay outcome remain separate gates; passing one does not silently promote the others.
