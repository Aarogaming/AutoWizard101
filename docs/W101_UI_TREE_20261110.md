Task `W101-UI-TREE-17`, workstream `CORE-TRANSITIONS`. This source checkpoint
adds a bounded observer through the existing CLI, scheduler and control owner.
It sends no gameplay inputs and is not installed. The initial archived hook was
incompatible; the reviewed subset from the maintained Deimos development branch
now passes bounded live reads, restoration and disconnect on the exact current
executable. Native Idle, settings and the X prompt have live evidence; shop and
pay-to-play menus have saved-trace recognition. Private Quinn's spoken dialogue
also passed its separately coordinated check. It remains open: the user clarified

## Architecture and reuse

`--cli ui-tree-watch` requires both `--enable-client-observation` and
`--enable-ui-tree`, the explicit repository workspace, and the complete selected
window identity. Default duration is 15 seconds; the permitted range is 1–60.
Opening Maelstrom, listing windows or viewing history never enables this reader.
The independent visual workflow remains available.

The native `W101UiTreeOperation` uses `WizwalkerWorker`'s existing supervised
transport, exact target checks, artifact records and exclusive `GameInputLease`.
There is one connection and one worker. The old hook-free loading adapter and
its version-1 protocol remain unchanged. The new observer pins its own source,
that common helper, the interpreter, the legacy source tree and the selected
client executable. It does not launch the legacy application or activate all
of its hooks. No new dependency was added.

## Different rates without competing readers

| Signal | Requested cadence | Behavior |
| --- | --- | --- |
| Loading flag | Every 250 ms | Unknown or loading invalidates current UI candidates. |
| Bounded visible UI tree | Every 1,000 ms, initial 125 ms offset | Requires a recent clear loading sample, then checks loading again afterward. |
| State stability | Two consecutive trees | Reports agreement from the same source, not independent confirmation. |

Reads are serialized, timestamped separately, and missed intervals are dropped.
This is not a hard real-time rate guarantee. A slow tree can delay the next
loading read; no queued backlog accumulates. The source worker has one executor
thread, below-normal process priority, bounded read deadlines and the existing
384 MiB supervisor limit. Visual or user observations are still needed to qualify
what a named control means on the current game client. PWM does not provide that
independence; staggered sampling and independent observations do.

The observer limits each projected tree to 384 nodes, depth 16 and 128 KiB of reads, and
limits its trace to 4 MiB. Chat, whisper, friend, account, password, login and
guild branches are excluded before reading descendants or text. It retains
structural names and only selected static Idle/NPC-title text, not arbitrary
dialogue, chat, credentials or memory addresses. Invalid pointers, changing
child vectors and budget overflow are unavailable observations, not empty trees.
Known decorative HUD/compass branches retain their root node but skip descendants;
settings/service panels also stop at the structural node needed for recognition.
This is a projection for the four declared states, not a dump of every UI control.

## Hook lifecycle and limits

Unlike the existing hook-free loading read, this reader uses wizwalker's
`RootWindowHook` to obtain the current root pointer. This includes temporary
client code writes under the owner's W101 exception; observation-only describes
its purpose, not OS read-only access.

Review found a legacy restoration gap: the handler cleared 3,900 scratch bytes
but saved only a pattern-length prefix. `RootScope` instead preserves the whole
baseline without clearing it, checks the exact original seven-byte entry
instruction before any write, and installs only the small reviewed root hook.
Partial setup is tracked. Cleanup restores/verifies the entry, waits briefly for
in-flight execution, restores the small hook body, verifies the entire scratch
baseline, and releases the export only after those checks. The process handle is
closed even when restoration fails. Failure is reported under the shared owner
and blocks later gameplay through the existing recovery guard; saving a normal
result cannot bypass that hold.

These measures do not prove race-free patching, compatibility with a future
client, or account safety. The brief settle delay is not a proof that every
client thread has left the hook. Live qualification must be bounded and verify
restoration before a subsequent test. Network manipulation and installed game
file writes remain excluded.

Client-side movement is a separate capability: the reviewed legacy `goto`
helper still sets yaw and sends W, so its existence does not establish
focus-independent walking. It is not enabled by this observation command.

## Live qualification procedure

First send the requested question notification for readiness. Start with a
five-second check while the user leaves W101 in native Idle. Verify hook
restoration, worker exit and clean shared guard before any further attachment.
Then, if the first check passes, coordinate a bounded menu/prompt/dialogue watch
with a question notification after its ready event; the user changes screens.
No desktop controller, movement, pet energy, snacks, Crowns or volume change is
part of this observer check. Return to Idle only when it has no unapproved game
consequence; quest dialogue is an explicit exception. Preserve
unknown states instead of guessing from stale names or a clear loading flag.
