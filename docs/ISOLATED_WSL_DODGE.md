# Isolated visual Dodge test on this PC

Maelstrom can run the local Godot Dodge demo in the existing Ubuntu WSL 2 VM using a private, off-screen X11 display. The controller reads rendered frames with the existing Dodge visual specialist, resolves actions through the selected Dodge pack, and sends bounded keys to that private display. It does not activate a Windows window or read host keyboard events.

The default isolated-test pack now includes an identification rubric, game states, and movement constraints; see [Game context and identification](GAME_CONTEXT.md). Choose a context-aware Dodge pack for this test. The legacy Dodge pack remains available for the older test paths.

In **Game workspace → Local test games**, choose this AutoWizard101 folder, optionally choose a Dodge pack, and select **Run isolated visual Dodge test (WSL)**. Open the test report folder to inspect the result and before/after frames. A run allows up to 20 actions, with a 28-second controller budget and a 40-second guest timeout. It stops on an unknown outcome or after three consecutive frames fail to locate a previously seen player. The experimental recovery candidate may re-observe an unknown after-frame twice without repeating the input before stopping. Each run records its seed to help investigate results; live timing and scheduling mean a seed alone does not reproduce a run exactly. The display has no network namespace access; it uses a private socket and software rendering with one configured rendering thread. These settings limit this test, not the entire WSL VM or your system.

This is an experimental setup prepared on this PC, not an automatically provisioned Windows VM. It requires the existing Ubuntu WSL 2 distribution, default `/mnt/<drive>` Windows mounts, unprivileged user/mount/network namespaces and overlayfs, plus the project-local tools under `.local/wsl-dodge-tools` and the isolated game copy under `.local/wsl-dodge-game-check`. The Linux Godot 4.7.2 archive was verified against the SHA-256 in the [official release](https://github.com/godotengine/godot/releases/tag/4.7.2-stable); the Xvfb, xdotool, and support packages came from authenticated Ubuntu package indexes and were unpacked locally. These tools are not installed into Ubuntu's system directories or shipped as application dependencies. WSL itself remains shared with any other WSL work.

## Controlled training pace

For the optional stepped test, first run `scripts/prepare_wsl_step_game.ps1` from the repository. It copies the existing Dodge source into a separate `.local/wsl-dodge-step-game` and refuses to overwrite an existing copy. Select **Stepped: 25% speed**, **50%**, or **100%** in Local test games, then run the isolated visual test. Real-time testing remains available. The stepped copy pauses between requests and advances a bounded number of frames with a fixed 30 Hz test clock. Its test-only control channel provides ticks, not game or enemy state: the policy still sees rendered images and chooses its own next move. Slower settings use more frames for the same simulated time, allowing finer simulation steps and more time for observation. Runs use random starting seeds by default; a controlled command-line test can specify a seed and speed.

Each stepped test has a 55-second wall-clock budget, a 70-second guest timeout, and limits of 40 actions and 180 requests. It may re-observe an unclear frame twice without issuing another input. A report records its seed, mode, speed, simulated game time and the reason it stopped. The comparison tool requires matching mode, speed, and limits. Compare multiple seeds at each speed independently; even with a matching start, different decisions can create different enemy encounters. Identical timestamps or seeds do not guarantee identical rendered pixels or generalize to other games. Censored runs do not establish how long the player would have survived.

The separate, longer score-goal test and its evidence are described in [Dodge endurance training](DODGE_ENDURANCE_TRAINING.md). Select the score-50 option in Local test games to run it in the private display.

Temporary display, mount, and network namespaces are removed when the test exits. The tools, isolated game copy, and `.local/wsl-dodge-runs` reports remain in the workspace. The game copy starts a seeded round automatically for testing using `tools/fixtures/godot_dodge_wsl_bootstrap.gd`; it does not provide player state to the controller. If the optional components are missing, Maelstrom reports the missing path. No automatic downloader is included yet.

On the first end-to-end visual run, two left movements were observed; a third action produced an unrecognized after-frame and stopped as `unknown`. The tracker now requires a bright eye inside a player-colored component, filtering the translucent motion trails seen in those frames; it still rejects multiple plausible players. In development checks capped at 12 actions, two runs reached the limit with all 12 movements observed; another recorded nine movements before a game-over frame. In two subsequent checks with the 20-action cap, seeds 781 and 997 recorded four and seven observed movements respectively before a visually inspected game-over frame. The reports conservatively call those final outcomes `unknown`; automatic game-over recognition is not implemented. These short runs are not a measured accuracy rate or proof of long-term survival, Windows capture, or support for Wizard101. A regular Windows virtual desktop alone does not provide an independent active input desktop; Windows documents that only one desktop in the interactive window station is active at a time.
